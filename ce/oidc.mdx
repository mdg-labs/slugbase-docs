## What you'll accomplish

After this guide, you can configure OIDC identity providers so members can sign in with your organization's SSO instead of (or in addition to) email and password.

OIDC providers are **operator-managed**. Instance administrators configure them through deployment environment variables — workspace admins cannot add or edit providers in the UI.

<Callout kind="alert" title="Breaking change">
Earlier SlugBase releases allowed workspace admins to enter OIDC client secrets in **Settings → Workspace → Identity providers**. That UI has been removed. Provider definitions and secrets are no longer stored in the database — set `OIDC_{SLUG}_*` environment variables on your deployment instead.
</Callout>

## Prerequisites

- Access to your CE deployment configuration (Docker Compose, Kubernetes secrets, or equivalent)
- An OIDC application registered with your identity provider
- Issuer URL, client ID, client secret, and requested scopes from the provider
- `APP_BASE_URL` set to the externally reachable HTTPS base URL of your instance

## Per-provider environment variables

Each identity provider uses a **slug** — a short identifier such as `google`, `github`, or `okta`. Environment variable names follow the pattern `OIDC_{SLUG}_*`, where `{SLUG}` matches the slug you choose (for example, `google` → `OIDC_google_CLIENT_ID`).

| Variable | Required | Purpose | Example |
|----------|----------|---------|---------|
| `OIDC_{SLUG}_CLIENT_ID` | Yes | OIDC client ID | `…apps.googleusercontent.com` |
| `OIDC_{SLUG}_CLIENT_SECRET` | Yes | OIDC client secret | `<client secret>` |
| `OIDC_{SLUG}_ISSUER_URL` | Yes | Issuer / discovery URL | `https://accounts.google.com` |
| `OIDC_{SLUG}_NAME` | No | Display name on the sign-in page | `Google` |
| `OIDC_{SLUG}_SCOPES` | No | Space-separated scopes | `openid email profile` |
| `OIDC_{SLUG}_ENABLED` | No | Enable this provider (`true`/`false`) | `true` |

A provider is active when the required trio (`CLIENT_ID`, `CLIENT_SECRET`, `ISSUER_URL`) is present and `OIDC_{SLUG}_ENABLED` is not `false`.

<Callout kind="danger" title="Important">
Never commit OIDC client secrets to source control. Inject them via your secrets manager or a local `.env` file excluded from version control.
</Callout>

### Register the callback URL

In your identity provider's application settings, register this callback URL (replace `{slug}` with your provider slug and use your real `APP_BASE_URL`):

```
{APP_BASE_URL}/auth/oidc/{slug}/callback
```

For example, with `APP_BASE_URL=https://bookmarks.example.com` and slug `google`:

```
https://bookmarks.example.com/auth/oidc/google/callback
```

The URL must match exactly, including HTTPS and path.

### Docker Compose example

This example configures Google as a federated provider alongside SMTP and AI credentials:

```yaml title="docker-compose.yml"
services:
  slugbase:
    image: ghcr.io/mdg-labs/slugbase:latest
    environment:
      APP_BASE_URL: https://bookmarks.example.com
      FRONTEND_ORIGIN: https://bookmarks.example.com

      # Google OIDC (slug: google)
      OIDC_google_CLIENT_ID: ${OIDC_GOOGLE_CLIENT_ID}
      OIDC_google_CLIENT_SECRET: ${OIDC_GOOGLE_CLIENT_SECRET}
      OIDC_google_ISSUER_URL: https://accounts.google.com
      OIDC_google_NAME: Google
      OIDC_google_SCOPES: openid email profile
      OIDC_google_ENABLED: "true"

      # Optional: second provider (slug: okta)
      # OIDC_okta_CLIENT_ID: ${OIDC_OKTA_CLIENT_ID}
      # OIDC_okta_CLIENT_SECRET: ${OIDC_OKTA_CLIENT_SECRET}
      # OIDC_okta_ISSUER_URL: https://your-org.okta.com
      # OIDC_okta_NAME: Okta
```

Restart the SlugBase service after changing OIDC variables.

## What workspace admins see

Workspace admins and owners do **not** manage identity providers in the application. Federated sign-in is configured only at deployment time — contact your instance operator to add or change providers.

## Sign-in experience

After a provider is configured and enabled, the sign-in page offers federated sign-in alongside email and password. Users who authenticate via OIDC can still add a password later from **Account → Password** if they want direct sign-in as well.

MFA applies to password logins only — federated sign-in does not prompt for an authenticator code.

## Verify it worked

1. Restart the SlugBase service after setting `OIDC_{SLUG}_*` variables.
2. Open a private browser window and navigate to your instance sign-in page.
3. Complete federated sign-in with a test account. The user should land in the workspace they were invited to.

## Troubleshooting

| Symptom | What to do |
|---------|------------|
| Redirect error from provider | Confirm the callback URL matches exactly, including HTTPS and path |
| Invalid issuer | Verify `OIDC_{SLUG}_ISSUER_URL` and that discovery endpoints are reachable from the server |
| Provider not shown on sign-in | Check that all three required variables are set and `OIDC_{SLUG}_ENABLED` is not `false` |
| User not placed in workspace | Federated sign-in creates or links an account; admins must still invite users into workspaces on invite-only instances |
| Workspace admin cannot edit OIDC | Expected — identity is operator-managed. Update deployment environment variables instead. |
